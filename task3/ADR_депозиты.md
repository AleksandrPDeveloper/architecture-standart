Предложил бы перейти на более микросервисную архитектуру и потихоньку, начинать дробить монолит, точнее
не вписывать в монолит новую функциональность,
постарался бы разделить устаревший монолит интернет банкинга в рамках депозитов
для этого бы предложил сделать фронт на react js новую функциональность бэка вынести в springboot + bd через кафка
все это для масштабируемости и отказоустойчивости, потому что функциональность заявок работать будет отдельно от системы,
в случае выхода ее из строя на остальное не повлияет, с другой стороны можно масштабировать отдельные элементы.
С другой стороны react js мог бы работать со старым asp.net для пререндренных страниц через single spa.
Добавил бы апи шлюз для работы с бэками и повышения изолированности авторизации и безопасности.
Внедрил бы кафку, поначалу тоже для работе с депозитами, для отправки заявок в бд, с целью быстродействия и масштабируемости.
Сделал бы отправку в шлюз через сервис сообщений который, применяет политики в зависимости от типа или топика, и формирует
отправку в топки СМС шлюза, здесь потребуется доработка, не думаю что слишком сложная.
Поскольку депозиты вынесли в отельный сервис, АБС теперь не связан с заявками, поэтому клиент на delphi должен еще обращаться и в пг.
Кажется это возможно реализовать так же через триггеры и хранимые процедуры.
Для отправки смс о подтверждении депозита менеджером использовал бы outbox таблицу как триггер и отправку в кафку через дебизиум,
информации об подтверждении в сервис отправки смс.
Все каналы бы использовал зашифрованные, бд шифровал.
Важные данные бэкапировал. Предложил бы использовать k8s если еще не используется и перетянул бы все приложения в него.
Можно было бы настроить кластеризацию, и определить failover стратегию и балансировку.
Диаграмма получилась сложновата, но это с учетом требований и пожеланий.
1. Внедрение кафки(асинхронность)
2. Микросервисы (масштабирование)
3. Развязка от команды ядра интернет банка по отправке СМС
4. Вынос функционала по заявкам из АБС
5. Использовал уже имеющийся стек


### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Можно было бы не использовать react js или использовать его, но asp.net mvc использовать как rest api.
Возможен вариант asp.net mvc обращался бы по api к приложению на c# например для заявок.
Возможен вариант хранения заявок в MS SQL, при сохранении старой архитектуры
Возможен вынос блока отправки смс в отдельный сервис через rest api, менее производительный вариант.
Возможен отказ от кафки, в пользу синхронных вызовов, но это может привести к сильной связанности.

**Недостатки, ограничения, риски**

Основные недостатки много изменений и разработки, возможно большие ресурсы на разработку, нужно учитывать компромиссы с заказчиком.
Освоение работы с kafka для асинхронности, возможно увеличение срока внедрения.
Написание нескольких микросервисов, вместо допиливания монолита, возможно увеличение срока внедрения.
Сервис шлюз требует доработки не только со стороны внедрения кафки, но и кэширования если его нет.
При увеличении количества заявок, и прочих операций могут быть проблемы с отправкой СМС внешнего телеком провайдера.
Внедрение api-gateway тоже требует соответствующих компетенций.
Возможно решение слишком на будущее, если количество заявок будет не достаточно большим, 
т.е. решение может быть заточено на сильное масштабирование которое сейчас не нужно
однако в рамках цифровой трансформации этот риск может быть оправдан.
